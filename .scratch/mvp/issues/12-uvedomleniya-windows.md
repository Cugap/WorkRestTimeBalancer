# 12: Напоминания на Windows

**What to build:** На Windows напоминание об отдыхе приходит системным уведомлением, когда приложение свёрнуто или не на переднем плане; нажатие открывает экран отдыха. После паузы и конца рабочего дня напоминаний нет. Звук и напоминания отключаются в настройках.

**Blocked by:** 10 — Напоминания на Android.

**Status:** ready-for-agent

- [x] Системное уведомление приходит при свёрнутом приложении.
- [x] Нажатие на уведомление открывает экран отдыха.
- [x] Пауза и конец рабочего дня отменяют запланированные напоминания.
- [x] Отключение напоминаний и звука в настройках действует.

## Comments

- Ядро не менялось: раскладку считает тикет 10, Windows-адаптер её только исполняет. Всё, что ниже, — про `app/lib/src/notifications/rest_notifications.dart`, `app/lib/src/window_activation.dart` и `app/windows/runner/notification_shortcut.cpp`.
- Главная находка: на Windows у приложения без MSIX-идентичности, как у `flutter run`/debug-сборки, **немедленный** toast показывается, а **запланированный** (`zonedSchedule`) молча теряется. В журнале `Microsoft-Windows-PushNotification-Platform/Operational` это видно как событие 2416 «локальное уведомление получено» без 2418/3153 «отправлено в пул потоков / доставлено». Причина — у приложения нет ярлыка в меню «Пуск» с `System.AppUserModel.ID`. Проверено вручную: после создания такого ярлыка то же запланированное уведомление доставляется (2418 `NotificationSource=Scheduled`, 3153 «delivered to … on session 1»), а без ярлыка — нет.
- Поэтому раннер сам создаёт ярлык: `notification_shortcut.cpp` через `IShellLinkW` + `IPropertyStore` пишет `%APPDATA%\Microsoft\Windows\Start Menu\Programs\WorkRestTimeBalancer.lnk` с `PKEY_AppUserModel_ID = Com.Cugap.WorkRestTimeBalancer` и путём к текущему exe. Ярлык идемпотентно перезаписывается при каждом запуске, AUMID совпадает с `WindowsInitializationSettings` (комментарии в обоих файлах). Это ровно то, что делает установщик; у debug-сборки установщика нет.
- Гонка, найденная на реальной сборке: раскладка пустеет в тот же миг, когда отдых предлагается, то есть ровно в момент доставки toast. Прежний `cancelAll()` успевал снять toast из расписания до доставки — напоминание не видел никто (в `GetScheduledToastNotifications` 8 → 0, история пуста). Теперь адаптер помнит идентификаторы своих напоминаний, а на Windows отменяет их по одному (`cancel(id)`) и не трогает те, чей срок наступил (±1 секунда): такой toast система показывает и оставляет в центре уведомлений. На Android/iOS остался прежний `cancelAll()`.
- Нажатие: плагин отдаёт клик через тот же `onDidReceiveNotificationResponse` → `RestNotifications.onOpenRequested` → `_openRestScreen`, отдельной ветки не понадобилось. Проверено активацией COM-класса `{d49b0314-ee7a-4626-bf79-97cdb8a991bb}` — это ровно тот вызов, который делает оболочка Windows при клике по toast: обработчик сработал, фаза была `restOffered`, экран отдыха открылся.
- Windows не разворачивает свёрнутое окно по активации, поэтому экран отдыха открывался бы невидимым. Добавлен `activateAppWindow()`: `ShowWindow(SW_RESTORE)` + `SetForegroundWindow` через `dart:ffi` (`ffi` стал прямой зависимостью). Окно ищется `EnumWindows` по **своему** PID и классу `FLUTTER_RUNNER_WIN32_WINDOW`: класс одинаков у всех Flutter-приложений, и `FindWindow` по классу находил чужое окно (на машине одновременно работает другое Flutter-приложение). Ошибки только логируются, ритм не ломается.
- Звук: в `NotificationDetails` добавлены `WindowsNotificationDetails` с `WindowsNotificationAudio.silent()` при выключенном звуке. Проверено на реальной сборке: при `soundEnabled=false` toast содержит `<audio src="ms-winsoundevent:Notification.Default" silent="true" loop="false"/>`, при включённом — элемента `<audio>` нет (звук по умолчанию). Заголовок и текст («Пора отдохнуть», «Короткий отдых · 3 мин») вынесены в чистую функцию `planNotification` и покрыты тестами, чтобы звук на трёх платформах не разъехался.
- Отмена на паузе и в конце дня: ядро присылает пустую раскладку, адаптер снимает все запланированные toast'ы. Проверено на реальной сборке на смене состояния «отдых предложен»: 8 запланированных toast'ов исчезли из расписания Windows, а доставленный остался в истории. Пауза и конец дня идут тем же путём (пустая раскладка), в ядре это покрыто `reminders_test.dart`.
- Устойчивость: `initialize()` больше не роняет приложение — результат плагина проверяется, при `false`/ошибке напоминания просто выключены; `schedule` пропускает точки в прошлом (плагин не планирует в прошлое) и глотает `ArgumentError`; при старте снимаются напоминания прошлого запуска (Android и Windows их переживают), чтобы пауза/новый день не унаследовали чужое расписание.
- Ограничения Windows без MSIX-идентичности (проверено): `cancelAll()` и `cancel(id)` убирают **запланированные** toast'ы, но уже показанные из журнала/центра уведомлений не удаляют — `History.Remove` и `getActiveNotifications` требуют package identity. Список активных уведомлений в приложении не читается, поэтому «проверить, что toast висит» из кода нельзя.
- Наблюдения на этой машине: toast доставляется в сеанс (`3153 delivered to Com.Cugap.WorkRestTimeBalancer on session 1`), но баннер на экране не рисуется — в неинтерактивном сеансе подавлены даже контрольные toast'ы Windows (PowerShell со своим AUMID). Поэтому доставка подтверждена журналом платформы и `ToastNotificationManager.History` (в истории лежит наш toast с `<text>Пора отдохнуть</text>`), а не глазами; содержимое окна приложения снималось через `PrintWindow`. Пауза кликом мыши не проверялась: сеанс неинтерактивный, окно забирает фокус только с трюком `AttachThreadInput`, а координаты кнопок при этом уезжают; отмену пустой раскладкой проверили на предложении отдыха — это тот же вызов адаптера.
- Проверено: `dart analyze`, `dart test` (188 тестов), `flutter analyze`, `flutter test` (59 тестов), `flutter build windows --debug`, `flutter build apk --debug -P kotlin.incremental=false`. После слияния `mvp` (тикеты 10–11 переделали адаптер на шов `RestNotificationPlatform`) Windows-часть живёт в `PluginRestNotificationPlatform`, а проверки на реальной сборке повторены: запланированные toast'ы, доставка при свёрнутом окне, тихий `<audio silent="true">`, снятие пустой раскладкой и открытие экрана отдыха по активации.
- Для тикета 14 остаётся: ручной клик по настоящему баннеру/центру уведомлений в интерактивном сеансе (здесь баннеры не рисуются), поведение `SetForegroundWindow` при реальном клике (при COM-активации из скрипта окно разворачивается, но на передний план Windows его не пускает), напоминание при полностью закрытом приложении (нужен ярлык с `LocalServer32`, чтобы клик поднимал процесс, — это уже про установку/трей, тикет 13) и проверка на чистой машине без ранее созданного ярлыка.
