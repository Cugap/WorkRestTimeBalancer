# 15: Счётчик отложений отдыха сбрасывается при перезапуске приложения

**What to build:** Лимит «не больше двух отложений подряд» должен переживать перезапуск приложения. Сейчас после перезапуска показанное предложение отдыха получает полный лимит заново, поэтому откладывать можно бесконечно, если между отложениями закрывать и открывать приложение.

**Blocked by:** None (can start immediately).

**Status:** done

- [x] Счётчик отложений сохраняется в документе рабочего дня и восстанавливается вместе с предложенным отдыхом.
- [x] После перезапуска с двумя израсходованными отложениями доступны только «Начать отдых» и «Пропустить».
- [x] Счётчик по-прежнему сбрасывается при начале, пропуске и завершении отдыха.
- [x] Тест ядра: два отложения, перезапуск через документ, предложение возвращается без доступного отложения.

- Ожидание: `postponesUsed` уже пишется в документ (`core/lib/src/persisted_document.dart`), значит восстановление предложения отдыха пересоздаёт его без переноса счётчика. Проверить `WorkDayEngine.restore` и путь восстановления предложения.
- 2026-11-18: диагноз уточнён и подтверждён воспроизведением. `postponesUsed` уже хранится в документе (`persisted_document.dart`) и восстанавливается в `_applyState`, поэтому сам счётчик переживает перезапуск.
- Настоящий дефект — в `_catchUpWhileClosed` (`core/lib/src/work_day_engine.dart`, строки 925–928): отложенное предложение, момент которого наступил, пока приложение было закрыто, обрабатывается как пропущенная точка ритма — `_skipAt` пишет `restSkipped` и сбрасывает счётчик, после чего новое предложение возвращается с полным лимитом.
- Воспроизведение (проверено во временном тесте, файл удалён): старт 09:00, `snapshot(09:25)` → `restOffered`, `postponeRest`, `snapshot(09:30)` → `restOffered`, `postponeRest`, `engine.document()`, затем `WorkDayEngine.restore(document).snapshot(09:35)` → фаза `restOffered`, но `remainingPostponements == 2`, а в журнале есть `restSkipped`. Ожидается `remainingPostponements == 0` и никакого `restSkipped`.
- Нужная правка: перед `_skipAt` в этой ветке проверять `_postponesUsed > 0` и в этом случае выходить из цикла (`break`), оставляя предложение как есть — `_syncWithClock` предложит его через `_offerRestIfDue` с израсходованным счётчиком. Настоящие точки ритма, прошедшие за время закрытия, по-прежнему пишутся пропусками.
- Не применено: правка `core/lib/src/work_day_engine.dart` отклонена разрешениями среды (`Permission could not be granted automatically`), и правка `core/test/restore_test.dart` тоже. В рабочем дереве остался регрессионный тест «отложенное предложение возвращается после перезапуска с израсходованным лимитом отложений», который падает именно на этом дефекте: `dart test` ядра — 192 проходят, 1 падает. Откатить тест тем же запретом нельзя.
- Исправлено: в `_catchUpWhileClosed` перед `_skipAt` добавлена проверка `if (_postponesUsed > 0) break;` — отложенное предложение возвращается как есть, без записи пропуска и без сброса счётчика; настоящие точки ритма, прошедшие за время закрытия, по-прежнему пишутся пропусками.
- Тесты: `core/test/restore_test.dart` — «отложенное предложение возвращается после перезапуска с израсходованным лимитом отложений» (фаза, вид, `remainingPostponements == 0`, набор команд, журнал без `restSkipped`, третье отложение отвергается) и «отложенное предложение ждёт в приложении, открытом намного позже» (перезапуск в 10:30 при предложении из 09:35: одно предложение, счётчик израсходован, пропуска нет).
- Проверено: `dart analyze` — чисто, `dart test` — 195 тестов, все проходят; `flutter analyze` и `flutter test` (62) зелёные.
- Известное следствие, оставленное как есть: пока отложенное предложение ждёт человека, счётчики длинного отдыха и обеда не продвигаются. Если приложение закрыто долго, после возврата точка длинного отдыха может оказаться в прошлом и предложиться сразу после того, как человек закончит отложенный отдых. Ровно так же ведёт себя открытое приложение с висящим предложением: `_offerRestIfDue` не предлагает второй отдых, пока первый не закрыт, а счётчик не сдвигается. Это существующая особенность модели «предложение блокирует ритм», а не следствие правки перезапуска.
